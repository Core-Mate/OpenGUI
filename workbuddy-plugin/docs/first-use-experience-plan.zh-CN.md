# OpenGUI 首次使用体验方案

状态：体验规划，尚未实施。日期：2026-10-06。

基于当前 WorkBuddy 插件源码、安装指引及本轮审查。暂按“通用入门，首次成功后分流到 App 测试或内容运营”设计；不要求用户先提供业务账号或测试用例。保留现有工作台样式、白色任务输入框和输入框外固定的 `@opengui`。

## 1. 目标与范围

首次体验的完成标准：用户明确选择一台设备和执行方式，完成一个真实、简单的手机任务，看到与任务对应的结果，并知道如何开始自己的任务。

安装成功、工具可用、看到手机画面、任务成功是四种不同事实，分别验证、分别提示。点击示例、复制提示词和打开页面均不代表授权开始操作。

本次覆盖：安装结果、宿主加载、首次首页、准备条件、示例任务、执行反馈、失败恢复、结果与回访。不增加计费、OAuth、云手机或新的第三方统计 SDK；不改变既有账户要求。

## 2. 当前断点

- 安装器同时输出较长英文状态和五步中文说明，普通用户要理解 MCP、Hooks、Skills，并自行判断是否已加载。
- 安装器、连接器推荐提示词、Skill 回复、首页提示和示例弹窗分别维护文案，容易不一致。
- “先试一下”藏在场景示例弹窗；首次打开可能先出现登录弹窗，用户尚未了解产品就被打断。
- 模型选择在顶栏，设备和任务在主体，未准备好的条件只用一行文字解释。
- 当前独立首页依赖配置模型，聊天任务可以由 WorkBuddy 执行，两条路径的区别没有被充分说明。
- 报告更强调导出格式；用户第一次完成后，还缺少“下一步做什么”的明确入口。
- 本轮审查发现开始按钮刷新、修改任务后旧约束残留和独立运营任务预算初始化问题。体验方案必须与这些修复一起落地。

## 3. 主流程

安装结果 → WorkBuddy 确认加载 → 同一任务首页 → 补齐准备条件 → 明确开始 → 真实执行 → 结果核验 → 新任务。

引导可以跳过，必要的运行条件不能跳过。已有账号、模型和可用设备时，不重复讲解准备步骤；已有具体任务时，不强制替换成示例。

### A. 安装结束：只给当前下一步

安装器保留机器可读状态，普通用户先看到简短中文摘要，诊断日志折叠或另存。

| 实际状态 | 用户文案 | 主操作 |
| --- | --- | --- |
| 文件与配置写入完成，尚无宿主确认 | “OpenGUI 已安装，等待 WorkBuddy 确认启用。” | “在 WorkBuddy 中打开” |
| 宿主确认工具和技能可用 | “OpenGUI 已就绪，先完成一个简单任务。” | “打开任务首页” |
| 宿主还未刷新 | “当前聊天尚未加载 OpenGUI。请新建聊天后打开。” | “复制打开指令” |
| 文件授权被拒 | “安装未完成：WorkBuddy 尚未允许写入插件配置。” | 展示宿主支持的正常授权步骤及“重试安装” |
| 下载、校验或依赖准备失败 | “安装未完成：下载／校验未通过。” | “重试下载”，保留有效缓存 |
| 旧任务占用运行时 | “请先结束正在运行的 OpenGUI 任务，再继续更新。” | “查看处理步骤” |

直接打开按钮取决于实际宿主能力；不支持时提供可复制的 `@opengui`，明确让用户在聊天中发送。不能把拟议按钮当作已经存在的 WorkBuddy API。权限失败不得输出安装成功，也不得自动弱化宿主保护。

`/hooks`、`/skills`、版本号和路径放入“加载遇到问题”，只有实际检查失败才引导用户打开对应设置。宿主信任仍由用户在正常界面确认。

### B. Try it：产品内统一叫“先试一下”

建议连接器中的推荐提示词只保留三个方向，均打开同一个任务确认页面：

1. “先试一下：打开设置，再返回桌面。”完整、无需填写占位符的任务。
2. “测试我的 App。”打开测试任务模板，由用户补齐对象与预期。
3. “打开 OpenGUI。”进入空白任务首页。

正式内容运营放在首页的业务模板里，不作为默认首个任务。若宿主提供 Try it 区域，使用同一份提示词配置；若不提供，安装摘要中的复制入口承担这一作用。

Try it 可以填入任务或由用户明确发送到聊天，但不跳过任务确认页，也不自动点击“开始执行”。

### C. 首次首页：一个主任务区域

页面结构：

1. 简短价值说明：“让 OpenGUI 操作手机，并记录每一步结果。”
2. 首次推荐卡：“先试一下 · 打开设置并返回桌面”，按钮“填入示例”，次操作“直接写我的任务”。
3. 固定 `@opengui` + 白色可编辑任务框。
4. 紧邻输入框的准备区：账号、执行模型、执行设备。已就绪项目收起为简短摘要，只展开当前缺项。
5. 主按钮“开始执行”；旁边显示当前未满足条件及直接可点击的处理入口。

首次推荐卡可关闭，帮助中可重新打开。关闭引导只影响展示，不跳过账号、设备或模型校验。

不在首次加载时立即弹登录框。允许先看示例、填写任务，再通过明确的“登录并继续准备”进入现有手机号登录。登录后返回原任务、保留编辑文本；启动仍需单独点击。

聊天中已有任务时直接预填，隐藏首次推荐卡，优先展示“确认任务”。编辑后更新所有由任务派生的限制；运行开始后保持冻结。独立结构化设置不得静默消失，应在确认页中可见。

### D. 准备条件：按实际状态指导

| 条件 | 已满足 | 未满足时的下一步 |
| --- | --- | --- |
| 账号 | 显示脱敏账号 | “登录后可选择模型并保存偏好” → 登录 |
| 执行方式 | 显示实际选中的模型／WorkBuddy | “选择执行模型” → 打开模型列表 |
| 设备 | 名称、系统、连接状态和尾号 | “连接 Android 手机”或“启动模拟器” |
| 任务 | 可编辑文本 | 填入示例或输入自己的任务 |

账号、模型和设备可按任意顺序准备，页面响应状态变化。只有一台可用设备或已保存且仍可用的偏好时可预选；多设备明确选择，失效偏好不静默换机。

无设备时：主路径为 USB 手机，模拟器作为次路径。帮助按当前平台提供短步骤，每步配实际检测结果；“未授权”和“未发现”使用不同提示。展示预计需要额外下载时，提供已知大小与真实进度，不虚构时间。

模型列表加载失败、账号失效和没有配置模型分别提示。没有模型不能伪装成设备问题。当前独立首页不能直接使用已结束聊天的模型；MVP 明确这一限制并保留任务草稿，提供重试及返回聊天的说明。自动移交到聊天执行属于后续能力，需先验证宿主定向路由。

### E. 第一个任务：验证整个链路

推荐任务：

> 打开手机设置，确认设置页面已显示；再返回桌面，确认桌面已显示后结束。只进行页面导航，不修改设置。

点击“开始执行”后：

- 先显示“正在建立设备画面”，通过实际首帧检查后才能操作。
- 执行区展示两个步骤：“打开设置”“返回桌面”，完成状态必须关联实际观察结果。
- 保留“接管设备”“结束任务”入口；首次运行用一句提示说明用途，不强制用户中断任务练习接管。
- 如果用户编辑了示例，不再套用原示例的成功条件或步骤；按最终确认的任务执行。

成功不是脚本结束或页面跳转，而是两项结果均有观察证据，任务终态正确，控制已释放，报告可访问。受阻、取消和部分完成使用各自状态，不记为首次成功。

### F. 执行与通知：分工明确

右侧展示具体步骤、画面、审核及接管。左侧仅在任务开始、需要用户处理、受阻、结束时提供必要摘要，不重复每个点击或未变化的等待状态。

聊天发起任务沿用请求内事件通知；独立首页任务以右侧为主要进度入口。现有 MCP progress 不能保证唤醒已结束聊天，界面不承诺“可以关闭，完成后一定通知”。

通知需要具备任务归属和去重；多聊天不串任务。正常状态事件不能代替审核批准或结果证据。

### G. 完成之后：先讲结果，再给下一步

首次成功卡：

> 第一个任务已完成
>
> 已打开设置并返回桌面。你可以查看执行记录，或开始自己的任务。

主操作“开始我的任务”；次操作“查看执行记录”。报告导出保留，但不把四种文件格式全部作为首次完成后的主按钮。

新任务页提供“测试 App”“处理评论”“自由描述”三个入口，继续使用同一个可编辑任务框。账号、模型和可用设备偏好可保留，任务文本、旧计划和业务限制不从上一个任务隐式继承。

测试模板补齐应用、功能、数据、预期和停止位置。运营模板补齐账号／目标、范围、语气、数量／时限和内容审核；存在占位符时要求补齐，不把占位符当作真实任务。

## 4. 异常与回访

统一错误结构：发生了什么 → 当前任务是否已开始／暂停／结束 → 已保留什么 → 一个直接可用的下一步。

| 情况 | 处理 |
| --- | --- |
| 登录取消或验证码错误 | 返回原准备页，保留任务；错误就近显示 |
| 模型列表为空／超时 | 分别解释未配置与网络失败；重试不丢草稿 |
| USB 未授权 | 指向手机上的授权动作；只读重新检测 |
| 首帧超时 | 明确未开始手机操作；保留请求供重新发起，旧终态不被迟到首帧复活 |
| 执行中断线 | 暂停并保留原手机及任务，重连后按原恢复流程重新确认 |
| 人工接管 | 明确“由你控制”，用户交还后重新观察；不自动重放最后动作 |
| 内容审核 | 在待处理内容旁解释批准、修改、跳过；只跳过当前条目 |
| 关闭／重开工作台 | 按服务实际状态恢复展示；不以重开页面作为重新启动授权 |
| 重开 WorkBuddy／服务不可用 | 区分草稿与已归档任务；原页面链接失效时提供重新打开指引 |
| 升级用户 | 只显示相关能力更新，不再次强制通用体验 |
| 已有首次成功用户 | 默认进入普通新任务页，帮助中保留“再试一次” |

## 5. 实现建议

- 共用示例和引导文案定义，生成安装输出、连接器 examples 与页面模板，减少五处手写同步。
- 将“引导已看过”和“真实运行条件”分开保存。dismissed 不等于 ready；页面缓存不能授予控制。
- 引导偏好保存在插件已有私有目录中，按安装实例／账号及引导版本处理。不要仅依赖随机端口网页的 localStorage；浏览器端只作缓存。
- 引导记录最小包含：引导版本、用户是否关闭、首次任务是否真正成功、已看过的上下文提示。草稿与任务记录使用既有任务存储，避免再建另一套任务状态。
- 账号变更、模型列表变更、设备重查、任务编辑均触发完整就绪状态重算。已有隐式限制需要区分“从旧文本派生”与“独立显式设置”。
- 运营场景必须在执行前结构化初始化数量／时限约束，不能只向模型传一段提示词。
- 窄窗口下输入、缺项操作和开始按钮可顺序到达；按钮禁用原因同时以文字给出。登录弹窗支持键盘焦点管理、关闭及返回原位置。
- 不增加云端用户追踪。研发验收可使用本地、按需导出的阶段时间与错误类别，不包含任务正文、手机号、截图或验证码。

## 6. 分期与验收

### P0：可用基础

修复模型选择后按钮不更新、编辑后约束残留、运营预算缺失；处理当前 CI 依赖审计失败。同步最新 main，避免重复提交已有功能。公开安装入口仍需解决现有权限与版本问题，不以文案掩盖安装失败。

### P1：首次成功闭环

收敛安装完成提示；统一 Try it 示例；首页推荐卡、准备状态、延后登录；首个导航任务和成功后的下一步；常见失败及保留草稿。第一版不依赖主动唤醒聊天等尚未验证的宿主能力。

### P2：业务分流与回访

测试／运营模板的缺项检查、相关上下文提示、引导进度记忆、升级提示、恢复入口及安装诊断优化。

### 必须覆盖的验收路径

1. 全新安装：配置写入、宿主加载各自验证，首次入口可发现。
2. 安装权限拒绝：不报成功，有合法恢复路径。
3. 新用户、无设备：可理解产品并保留任务，按提示连接后继续。
4. 已登录且设备可用：跳过重复说明，直接确认任务。
5. 聊天任务：预填同一确认页，编辑后实际按最终请求执行。
6. 任意准备顺序：尤其最后选择模型时，开始按钮立即更新。
7. 示例首次成功：真实设备或支持的模拟器，有两个步骤的观察证据及报告。
8. 首帧超时、模型失败、断线：状态真实，不误记首次成功。
9. 多聊天与独立首页：通知不串任务、不刷屏、不承诺未支持的唤醒。
10. 关闭引导、取消登录、刷新、重开：文本和状态按承诺保留；不偷偷开始。
11. 运营模板：占位符未填阻断；审核与条数／时限落实到执行器。
12. 390px 窄工作台与桌面：无横向溢出，键盘可完成准备和启动。

建议用少量首次使用者做可用性测试，观察是否能在无需旁人解释的情况下完成首个任务。记录安装到首页、准备耗时、准备完成到首个成功、失败类别与恢复成功率；把设备下载和人工授权等待单独记录，先测基线再设目标，不把未经实测的“两分钟上手”写成承诺。
