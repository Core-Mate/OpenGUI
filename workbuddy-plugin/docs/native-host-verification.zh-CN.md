## 自带 headless 引擎检查

新增 `npm run test:host`，在构建后调用真实 WorkBuddy 应用中随包分发的 headless CLI。可以传入绝对应用路径：

```sh
npm run test:host -- /Applications/WorkBuddy.app
```

脚本只创建自己的临时配置与空工作目录，通过 ACP v1 `initialize`、`session/new` 建立本地协议会话，让引擎加载当前构建的 OpenGUI MCP。消息形状依据 [ACP 官方会话说明](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v1/session-setup.mdx)。MCP 使用严格指定的测试目录，不修改用户实际 MCP／Hook 配置，不复制账号凭据，不发送模型提示词。

临时 MCP 通道只转发目录和初始化请求，所有 `tools/call` 在到达插件前明确拒绝。保存的证据只有工具名称、参数结构是否存在及被拒绝调用数；没有保存任务输入、推理或凭据。检查结束后清理测试进程组和临时目录。

## 当前桌面安装的差距

只读检查实际 `.workbuddy` 配置，OpenGUI MCP 已配置、没有禁用，Node 与入口文件存在；七种生命周期 Hook 均各有一条 OpenGUI 记录。

但其安装包虽同为 `0.3.1`，文件与当前构建不一致：缺少 `workbench-page.js`、`configured-runner.js`、`ios-simulator.js`、`connection-diagnostics.js`，已有 `mcp.js`、`service.js` 与 Skill 内容也不同。因此不能用版本号或“已配置”推断本轮能力已加载。

升级检查检测到旧 broker 仍监听，并通过认证握手确认其为正在运行的 OpenGUI。安装器返回 `upgrade_blocked`；未覆盖安装、停止旧运行时或撤销现有任务。

此前桌面工具报告 Mac 锁屏。后续复查已能读取真实 WorkBuddy 窗口，当前显示旧任务已完成，旧设备墙提示服务已退出；无需再次解锁。升级检查仍确认旧运行时占用入口，实际 MCP 仍启用。此前退出旧插件的确认尚未收到；待旧 MCP 正常退出后可用已核对候选包升级，再在 `/hooks` 和 `/skills` 中完成实际宿主检查。

## CLI 入口注意

此 WorkBuddy 发行包没有完整交互 TUI 的 `dist/codebuddy`。直接运行某些管理子命令会落到缺失的 TUI 入口；本脚本使用随包入口已支持的 `CODEBUDDY_FORCE_HEADLESS_BUNDLE=1`，不修改应用文件。

脱离桌面启动的普通 CLI 默认配置不等于 `.workbuddy` 中的实际 MCP 配置。一次 CLI `mcp list` 返回空目录不能证明桌面没有配置；本次引擎测试使用明确的隔离配置，桌面状态另行核对。
